# windevolve_sdwpf

Evolutionary model discovery for wind power forecasting on the **SDWPF / Baidu KDD Cup 2022** dataset.

This folder contains the evaluation harness, a tiered set of baselines, and the OpenEvolve configuration used to search for forecasting programs. Every method here is scored with the **official competition metric**.

---

## Layout

```
windevolve_sdwpf/
├── official_metrics.py         # official scorer, verbatim  (do not modify)
├── test_data.py                # official window loader  (do not modify)
├── val_windows.py              # builds the held-out validation split  (do not modify)
├── evaluator.py                # OpenEvolve-facing evaluator  (validation split)
├── competition_score.py        # final leaderboard-comparable scorer  (final_phase_test)
├── initial_program.py          # persistence seed, evolved by OpenEvolve
├── config.yaml                 # OpenEvolve configuration
├── val_split/                  # generated by val_windows.py
│   ├── val_windows/            #   infile/*in.csv + outfile/*out.csv
│   └── val_train.csv           #   training CSV truncated before the val period
└── baseline_models/
    ├── naive/              # no training required
    │   ├── baseline_naive.py
    |   ├── baseline_climatology.py 
    ├── classical/     
    │   ├── baseline_arima.py  
    ├── tree/
    │   ├── baseline_gbdt.py
    └── gru/
```

Each model has a `.md` beside its `.py`. Trained artefacts live next to the model
that produces them, so `gbdt_model.joblib` and `checkpoints/` resolve relative to
their own file and need no configuration.

## Contents

### Evaluation harness

| File | Purpose |
|---|---|
| `official_metrics.py` | The real Baidu submission grader, copied **verbatim** from `kddcup22-sdwpf-evaluation/paddlepaddle/metrics.py`. Masking rules, kW→MW, per-turbine MAE/RMSE, sum across turbines, degeneracy guards, latest-24h score. md5-identical to upstream. |
| `test_data.py` | Faithful copy of the official per-window loader. Slices one window CSV into 134 per-turbine blocks. |
| `val_windows.py` | Builds a held-out validation window set from the tail of the 245-day CSV, in the official on-disk format, plus a truncated training CSV. Run once. |
| `evaluator.py` | The OpenEvolve-facing evaluator. Loops the **validation** windows, calls a program's `forecast(envs)`, scores through `official_metrics.py`, returns a metrics dict. Never raises. |
| `competition_score.py` | The final scorer. Reproduces the official `evaluation.py` end to end against `final_phase_test`. Run **once**, at the end, on the champion. |

Why two scorers: they use the **same ruler** — both delegate to `official_metrics.py` — and differ only in which windows they point at and in what they do on failure. `evaluator.py` converts every failure into a penalty so the search never crashes; `competition_score.py` raises, exactly as the competition does.

`evaluator.py` is also deliberately **stricter** than the official grader: it validates each candidate's raw output (shape, finiteness, per-turbine horizon variation) before the grader sees it, because the official guards have a hole that an evolutionary search will find. `competition_score.py` adds nothing — see the next section.

### Forecasting programs

Every program exposes the same contract, so all are scored identically:

```python
forecast(envs) -> np.ndarray   # shape (134, 288, 1), active power in kW
```

`envs["path_to_test_x"]` is the path to one test window; the program reads it itself. `envs` also carries `path_to_train` (the training CSV) and `path_to_locations` (turbine x/y) for methods that fit a model.

Because `forecast()` is called **once per window**, any loading or fitting must be cached at module level and done once.

### Documentation

Each model has a `.md` beside its `.py` explaining the method, its parameters, and its caveats. `baseline_models/gru/gru_baseline.md` covers the GRU in depth.

## Equivalence with the official evaluator

`competition_score.py` was checked against the **genuine, byte-unmodified** official
evaluator — not a reimplementation of it. The check ran
`kddcup22-sdwpf-evaluation/paddlepaddle/evaluation.py` (md5 `e0eab7f963…`),
`metrics.py` (`af901786d5…`) and `test_data.py` (`bd9dbef3b7…`) against a real
submission `.zip` containing `prepare.py` and `predict.py`, with windows packaged
in the official nested form `test_x.zip → NNNNin.zip → NNNNin.csv`, entering
through `evaluation.eval(submit_file)` — the actual competition entry point. The
only runtime change was `NUM_MAX_RUNS` 142 → 3, set as a module attribute rather
than by editing the file, because the check used the 3-window toy dataset.

The same forecaster was then run through `competition_score.py` against the same
windows as unzipped CSVs.

```
OFFICIAL evaluation.py : {'score': -84.33595515367846, 'ML-framework': 'paddlepaddle'}
competition_score.py   :            84.33595515367846
delta                  :             0.00e+00
```

Identical **per window**, not merely in aggregate:

| window | official (RMSE / MAE / acc) | `competition_score.py` | max delta |
|---|---|---|---|
| 0 | 73.1092 / 59.4201 / 45.75 % | 73.1092 / 59.4201 / 45.75 % | 0.00e+00 |
| 1 | 117.0413 / 100.7190 / 22.11 % | 117.0413 / 100.7190 / 22.11 % | 0.00e+00 |
| 2 | 85.3667 / 70.3593 / 32.66 % | 85.3667 / 70.3593 / 32.66 % | 0.00e+00 |

**Gate parity.** The same degenerate submissions were pushed through both paths:

| case | official `evaluation.py` | `competition_score.py` |
|---|---|---|
| all-zero prediction | REJECTED | REJECTED |
| constant 500 everywhere | REJECTED | REJECTED |
| NaN in prediction | REJECTED | REJECTED |
| 40 % of turbines zeroed | REJECTED | REJECTED |
| huge error (accuracy gate) | REJECTED | REJECTED |

The rejection messages match character for character, apart from official's outer
`eval()` wrapper adding `Err: … (submission.zip)`. The accuracy value in the gate
message agrees to three decimals (`-172.828`), so the whole
`latest_rmse → acc` chain matches, not just the accept/reject verdict.

### The four permitted differences, and nothing else

| # | official | ours | affects the number? |
|---|---|---|---|
| 1 | takes a submission `.zip`, loads `prepare.py`, calls `prep_env()`, checks the declared `framework` against the evaluator's directory name | takes a path to a `.py` exposing `forecast(envs)` | no |
| 2 | `test_x.zip → NNNNin.zip → csv` | `<test_dir>/infile/NNNNin.csv` | no |
| 3 | returns `{"score": -84.335955, "ML-framework": "paddlepaddle"}` (higher-is-better leaderboard) | returns `84.335955` (lower-is-better), no framework key | no — sign convention and submission bookkeeping |
| 4 | **raises** on the 10 h `MAX_TIMEOUT` projection | same computation, printed as a `WARNING` | no — resource gate, not a metric |

**On the `ML-framework` key (row 3).** It is submission bookkeeping, not part of
the metric. The grading server holds four *identical* copies of the evaluator —
`base/`, `paddlepaddle/`, `pytorch/`, `tensorflow/` — and `evaluation.py:211-215`
only checks that the string a submission declares in `prepare.py` matches the
directory the evaluator is running from. It routes a submission to a copy of the
same code; it never enters the score. Our stack is PyTorch (the GRU baseline is a
PyTorch port), so a real submission would declare `"pytorch"` and be graded by
`pytorch/evaluation.py` — byte-identical to the `paddlepaddle/` copy used above.
The check above used `"paddlepaddle"` purely because that is the copy Baidu
published to GitHub.

**On the timeout (row 4).** This is the only *behavioural* deviation. The 10-hour
budget was measured on the competition's 4-core / Tesla V100 box. Raising on our
hardware would reject programs the competition would have accepted; ignoring it
would hide a genuine overrun. So the projection is computed exactly as official
does (`left_time -= cost_time`; `i > 1 and left_time < MIN_TIME * (cnt_left_runs + 1)`,
`MIN_TIME = 3`) and reported rather than enforced.

Everything else is reproduced, including the parts that only matter in the failure path:

- `initiate_env()` constants, with `min_non_zero_ratio = 0.9` and `min_distinct_ratio = 0.1`
- `performance()`: raise on negative `latest_rmse`; `acc = 1 − latest_rmse / capacity`
- per-window accuracy gate, rejecting at `acc <= 0`
- per-window print of RMSE / MAE / Score / Accuracy
- `NUM_MAX_RUNS` completeness gate with the **65535 sentinel** — an incomplete run
  returns `competition_score = 65535` and `total_mae = total_rmse = -1`, exactly
  what official hands the leaderboard as `-65535`
- `MIN_NOISE_LEVEL = 0.05` across-window std floor on rmses / maes / accuracies,
  reached only on a complete run
- `is_debug` timing prints

> **Which `metrics.py`?** PaddleSpatial ships two files by that name.
> `kddcup22-sdwpf-evaluation/paddlepaddle/metrics.py` is the submission grader —
> that is the one copied here. `apps/wpf_baseline_gru/metrics.py` is a local
> development scorer: it has no NaN condition in its mask and drops `Patv <= 0`
> only when `Wspd > 2.5`, so it scores rows the real grader discards. On identical
> inputs it reads **4.46 % higher** (90.35 vs 86.49), which is larger than the
> whole spread of the baseline table. Do not use it.

## Search vs. final evaluation

**This is the most important protocol decision in the project. Read it before running a search.**

`final_phase_test` is the official 142-window competition test set. It is the basis for any claim of comparability with the KDD Cup leaderboard, and it can only serve that purpose if it is **never used as a search signal**.

An evolutionary search that maximises a score computed on `final_phase_test` is optimising against the test set directly. After 60 iterations, the resulting champion score is no longer held out: it has absorbed information from the very windows it is meant to be evaluated on. Competition teams got one submission against those windows, not sixty rounds of feedback, so the two numbers are not comparable. 

The protocol used here:

| Phase | Data | Scorer | Used for |
|---|---|---|---|
| **Search** | `val_split/val_windows/` | `evaluator.py` | every candidate evaluation, every ablation, model selection |
| **Final** | `final_phase_test/` | `competition_score.py` | scored **once per arm**, at the end, on the selected champion |

`val_windows.py` builds the validation split from the last 30 days of the 245-day CSV, sampling window origins with a fixed seed so the split never changes. It also writes `val_train.csv`, the training CSV truncated to end *before* the validation period — a candidate that fits on the full 245-day file would otherwise be training on its own validation targets.

Note that the champion is refit on the **full** 245-day file at final scoring but on the **truncated** file during search. That is the correct anti-leak design, but it means some validation→test movement is expected and is *not* overfitting. Report it as a design choice.

The **generalisation gap** (validation score minus final score) is itself a reportable result, and is expected to be non-zero. Report it rather than hiding it.

### Building the split

```bash
python val_windows.py                                  # 30 val days, 40 windows, seed 1
python val_windows.py --val-days 30 --n-windows 40     # explicit
```

Run this **once** and do not re-run it with different parameters mid-project. Changing the split invalidates every comparison made against the old one.

## Setup

The data is **not** in this repo. Point the harness at it with environment variables (or edit the constants at the top of each scorer).

**Search — `evaluator.py`:**

```bash
export SDWPF_VAL_WINDOWS="$PWD/val_split/val_windows"
export SDWPF_VAL_TRAIN="$PWD/val_split/val_train.csv"
export SDWPF_LOCATION_FILE="/path/to/sdwpf_kddcup/sdwpf_baidukddcup2022_turb_location.csv"
```

**Final — `competition_score.py`:**

```bash
export SDWPF_TEST_DIR="/path/to/sdwpf_kddcup/final_phase_test"
```

`final_phase_test/` must contain `infile/*in.csv` and `outfile/*out.csv` (142 windows). It is read **only** by `competition_score.py`; `evaluator.py` has no path to it.

## Usage

All commands are run from the package root (`windevolve_sdwpf/`).

**Build the validation split (once):**

```bash
python val_windows.py
```

**Score one program on the validation split:**

```bash
python evaluator.py initial_program.py
SDWPF_MAX_WINDOWS=10 python evaluator.py initial_program.py     # first 10 windows
python evaluator.py baseline_models/classical/baseline_arima.py
```

**Train the models that need it:**

```bash
python baseline_models/tree/baseline_gbdt.py --origins 150
python baseline_models/gru/gru_baseline.py --turbines 0-133 --device mps
```

Both are resumable: the GRU skips turbines whose checkpoints already exist. Train them on `val_train.csv`, not the full 245-day file, or their validation scores are meaningless.

**Run the evolutionary search:**

```bash
export OPENAI_API_KEY="<key>"
export SDWPF_VAL_WINDOWS="$PWD/val_split/val_windows"
export SDWPF_VAL_TRAIN="$PWD/val_split/val_train.csv"
python -m openevolve.cli initial_program.py evaluator.py --config config.yaml
```

**Final measurement (once, at the end):**

```bash
python competition_score.py <champion.py>
```

A capped run returns the official sentinel rather than a partial score, so for a
deliberate subset smoke test set both variables:

```bash
SDWPF_MAX_WINDOWS=3 SDWPF_NUM_MAX_RUNS=3 python competition_score.py <champion.py>
```

## The metric

For each turbine, ground-truth steps that are missing or invalid are **excluded** (not zeroed):

- any NaN in the row
- `Patv < 0`
- `Patv == 0` while `Wspd > 2.5` — a stopped turbine
- any pitch angle `Pab* > 89` — blades feathered
- `|Wdir| > 180` or `|Ndir| > 720` — sensor out of range

On the surviving steps, MAE and RMSE are computed in **megawatts**, then **summed across the 134 turbines** to score one window, then **averaged across windows**:

```
score = 0.5 * (RMSE + MAE)      # lower is better
```

Because errors are summed over turbines, a method must work well on **all** turbines — a few bad ones dominate the total.

**Sign convention:** `evaluator.py` returns `combined_score = -competition_score` because OpenEvolve maximizes. A valid score is therefore **negative** (roughly −40 to −70). Failures return `−1e6`, always by returning rather than raising, since a raised exception would be replaced by fitness `0.0` and wrongly outrank real programs. `competition_score.py` returns the score **positive**, lower-is-better.

**Prediction sign is not checked, deliberately.** About a third of real SDWPF `Patv` readings are negative (idling turbines drawing power; min ≈ −8 kW), so persistence emits negative forecasts as a matter of course. The official grader accepts this: its mask drops negative rows from the *ground truth* but never inspects the sign of a *prediction*. A non-negativity rule would reject our own baseline.

**Degeneracy guards:** the official scorer rejects predictions that are all-zero or (near-)constant across the farm. A flat per-turbine mean is rejected outright — which is why `baseline_climatology.py` varies by time of day rather than emitting a single number, and why true lag-1 persistence is unscoreable.

**The guards have a hole, and `evaluator.py` closes it.** `is_zero_prediction` tests `np.any()`, so a constant `1e-3` counts as non-zero, and `is_identical_prediction` only requires 10 % of turbines to vary. Measured: pinning 89 % of turbines to a constant `1e-3` passes **both** official guards and scores ~19 % better than honest persistence. `evaluator.py` therefore rejects a candidate when more than 25 % of turbines have a near-constant horizon (std < 1 kW). Calibration: honest forecasters sit at 0.010–0.015 on that statistic, exploits at 0.51–0.89. This check is **search-time only** — `competition_score.py` stays a faithful mirror.

**Shrinkage is legitimate, not gaming.** Uniformly scaling predictions down improves the official score substantially (persistence 86.49 → 62.39 at scale 0.25), because shrinking an uninformative forecast toward the conditional mean is the correct response under MAE/RMSE. No magnitude floor is imposed, since one would penalise well-calibrated uncertainty. Expect the search to find shrinkage early; report a shrinkage-optimised persistence control alongside the champion so credit goes to the right place.

**Noise floor:** before drawing conclusions from any ablation, measure the seed-to-seed standard deviation of a trained baseline on the validation split. The entire top ten of the original competition spanned about 0.4 MW, so an unmeasured noise floor can easily exceed the effect being studied.
